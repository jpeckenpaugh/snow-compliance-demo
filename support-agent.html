Proposed support layer · bounded and human-in-the-loop

A support agent that knows what it must not do

Field the predictable requests around webcam verification — camera trouble, retries, lockouts, accommodations, consent withdrawal, appeals, and audit questions — without letting a chat message become an auth bypass.

Bounded, not a general chatbot This assistant explains policy, triages a known situation set, and opens approved human workflows. It never approves access, changes a role, unlocks an account, deletes audit records, disables liveness, or reads raw photos, embeddings, or another employee's data. Unknown or low-confidence requests go to a person.
Why

The login flow creates a predictable support tail

Most verification support is explanation and routing, not a decision. That is the safe scope for an agent: answer from approved policy, check the caller's own status, and create the right human request.

Explain

Camera permissions, lighting, liveness retries, review-band results, fresh step-up, retention, and who can view a photo.

Triage

Map the message to one catalog situation with a confidence score. Ambiguous or unknown requests are handed off.

Start a workflow

Open an assisted-verification request, a device ticket, an unlock ticket, an appeal, or a privacy case.

Protect the boundary

No auth decisions, no biometric payloads, no cross-user reads, no role changes, and full audit.

The catalog is data, not prompt text. Changing a situation or tool requires review, tests, and a new agent release.

Architecture

Model for language, code for authority

Chat widget (authenticated session)
        |
        v
Support API ---> SUPPORT schema (redacted transcript, intents, tool calls, escalations)
        |
        +--> Orchestrator
        |      +--> intent classifier (catalog code + confidence)
        |      +--> policy engine (scope, allowlist, human gate)
        |      +--> retrieval (approved KB only, citation required)
        |      +--> response composer (low temperature, JSON schema)
        |      +--> tool gateway (self-only, validated args, approvals)
        |
        +--> Human console / queue (warm handoff, SLA)
        |
        +--> Ticketing / HR / compliance case systems

The model never receives a database credential. It can propose an action, but the deterministic tool gateway decides whether that tool is allowed for the situation, whether it needs human approval, and which employee it may act on.

Safety

Guardrails that are enforced outside the prompt

RiskControl
Prompt injection / "ignore instructions"User and retrieved text are data; tool calls come from policy, not free text; tool names and arguments are validated.
Cross-user data requestNo cross-user tool exists; gateway derives employee ID from the verified session and ignores body IDs.
Photo or embedding requestBiometric tools are denied; the support schema has no grants on IDENTITY or the photo stage.
Credential phishing in chatNever ask for passwords, MFA codes, tokens, photos, or government IDs; redact volunteered PII before storage.
Hallucinated policyAnswers require an approved citation; no citation means "I cannot confirm" and a handoff.
Ambiguous or unknown requestOne clarifying question maximum, then handoff with the context.
Unauthorized actionHigh-risk tools require human approval; every invocation is logged with args and result.
Model or retrieval outageFail closed to a human queue; never fall back to an ungrounded answer.

Always denied: reading another user, raw photos, embeddings, centroids, role changes, account unlock, access approval, audit deletion, threshold changes, SQL passthrough, and HTTP passthrough.

RBAC

Separate service, human queue, and oversight

RoleCanCannot
SUPPORT_AGENTWrite conversations, intents, tool calls, escalations; read published KBRead IDENTITY, photos, embeddings, or other users' conversations
SUPPORT_HUMANRead assigned conversations, resolve escalations, log accessChange roles, unlock accounts, approve photo access, view raw photos
COMPLIANCE_ADMINManage KB and release config; review high-risk casesBreak-glass without two-person approval
AUDITORRead audit metadata and escalation historyRead raw transcripts or photos outside policy

Row access limits conversations to the employee and oversight roles. Every human transcript view writes an access-log row. The support service has no grant on the biometric schema or photo stage.

Rollout

Start narrow

  1. Define

    Approve the situation catalog, KB ownership, privacy review, and support SLAs. No production data.

  2. Schema and policy

    Apply SUPPORT DDL, row access, least-privilege roles, and deterministic tool gateway.

  3. Retrieval and UI

    Publish approved articles, add citations, build the chat widget with explicit action confirmation.

  4. Human console

    Queue, redacted context, SLA, resolution, and access logging for the support team.

  5. Red team and pilot

    Golden set, adversarial suite, 20-person pilot, accessibility review, then expand channels and languages.

Decisions requested

What the board needs to settle

  1. Phase-1 situation set and which situations are human-only from day one.
  2. Channels: web help only, or also email/chat/Slack.
  3. Cortex-hosted model vs. approved external LLM and its data boundary.
  4. KB ownership, review cadence, and support hours/SLAs per queue.
  5. Transcript retention and whether the agent may send a fresh challenge.
  6. Languages, accessibility requirements, and works council/union review.
